## 首版行为

医生从已保存病例详情进入“复查计划”，手填日历日期和原始说明。日期按北京时间日历日期保存，不代表预约时段，不做 UTC 时刻转换。输入先核对，勾选后明确提交；只有取得匹配的持久回执并重新读取服务器记录后才显示已保存。

每病例最多一个当前 M6 计划。更正将旧记录标为 cancelled 并另建一条；撤销只改变当前记录状态，不删除原文。医生可展开历史。来源不明的旧记录、多个当前计划、记录与回执不匹配时停止修改和导出，显示现存历史待单独核对，不自动收养或改写旧数据。

病例必须属于当前账号且未软删除。复查接口不接受 owner、status、done_at 或任意额外字段。没有自动建议、自动日期、完成标记、消息发送或预约接口。

## 数据与并发

- 只使用现有 `cases`、`followups`、`audit_log`，没有模型、字段、迁移、依赖或部署配置变更。
- 确认时锁定所属病例的 Case 行，与现有病例编辑和问诊写入使用同一锁；锁后重读完整复查集合。
- 集合令牌包含病例版本和全部复查行；预览令牌还绑定本次动作、原计划和新原文。过期令牌返回 409，不覆盖新计划。
- 客户端先可靠暂存账号/病例隔离的请求 ID，再发送确认。同一请求 ID 和相同内容重放只返回原回执；同 ID 异文拒绝。
- `audit_log.log_id` 由来源、病例、账号、请求 ID 的 SHA-256 构造。复查行和操作回执在一个事务提交，审计失败一起回滚。
- 通用审计 API 自行生成 UUID，不能伪造本功能的确定性回执 ID。没有删除或更新回执接口。
- 连接中断、提交应答丢失时只读查询回执。查不到回执不等于未保存；只允许再次明确核对后使用原请求 ID 和原内容重试，不自动新建请求。
- 首版每病例最多 200 条复查历史。超过上限不截断后继续写入；达到上限仍允许撤销当前计划。

当前标签页的未提交输入保留 8 小时，恢复后必须重新核对。待核对请求不按时间自动过期，也不在退出账号时清除；按账号和病例隔离，重新登录相同账号后可以核实原结果。读取或写入本地待核对记录失败时禁止新提交。关闭标签页会失去该标签页存储，需先核对服务器历史再决定后续操作。

## 文书与 KPI

两类 M2 草稿读取有效的已保存日期及医生原文；撤销后明确显示“当前无有效复查安排；此前计划已撤销”。未记录病例保留原缺失说明，不从预后文字推导复查。

文书确认快照升级为 v2，纳入复查集合状态。更正、撤销、改回相同原文均使旧确认失效。本标签页核实复查操作后主动重读已打开文书；其他客户端变更由下载接口拒绝旧快照。DOCX 仍为未签署医生核对草稿；宠主说明不原样交给宠主。

KPI 仅增加 cancelled 排除条件，使已撤销计划不进入复查分母及样本；不更改窗口、时区或历史指标算法。

## 验收证据与限制

专项测试：后端复查 16 项、文书生命周期 22 项、前端复查 18 项、病例详情文书 47 项通过。包括原文/日期、权限/软删除、无改动/非法输入、事务回滚、提交后连接失败、同请求重放、持久回执、历史冲突、草稿恢复和账号切换。

第一轮本地回归：后端七组共 114 项、前端 251 项、M2 模板校验、生产构建和路由体积检查通过；首屏 JS 为 454049 字节（门槛 460000），依赖审计 0 项漏洞。本地 Chromium 的 M6 七个流程场景通过并生成六份样本，但本地浏览器仅连接新建 SQLite 冒烟环境，不计为 PostgreSQL 验收。静态总门禁要求已提交且干净的工作区，须在本次本地提交后续跑；原门禁未修改。

候选提交前预算：1 轮实现修订、1 次完整本地回归；尚未消耗候选 CI。后续 CI 结果以草稿 PR 上绑定 HEAD 的运行记录为准。

本地容器没有可用原生 PostgreSQL，安装受到执行环境限制。因此真实 PostgreSQL 锁竞争与进程重启回读必须由 CI 的新建隔离数据库验收；SQLite 单元测试不能替代这一项。

CI 新增两个并发测试：不同请求竞争只成功一个；同请求同时提交只写一条计划及一条回执。控制连接先锁 Case 行，确认两个请求都处于 PostgreSQL 等锁状态，再释放；随后用独立连接查计数。更正和撤销后用另一个进程重新登录、读取历史/回执并重放旧请求。

Chromium 验收真实页面与隔离 API：显式恢复输入、勾选确认、并发导致旧计划及文书确认失效、服务已提交后丢响应、刷新后只读核实、撤销保留历史、两类文书预览/下载内容一致且不写入。
